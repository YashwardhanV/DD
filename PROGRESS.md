## Stress test (2026-10-06)
A hardening pass after stage 12: fuzzing, adversarial unit tests, a randomized cancel/resume stress test and an end-to-end run on 200,000 files. **9 bugs found and fixed**, each with a test that fails on the old code and passes now:

| # | Bug | Effect | Test |
|---|-----|--------|------|
| 1 | `drivedex copy E:\Photos E:\Photos\Backup` was allowed | every re-run copied the previous copy again, one level deeper (`Backup\Photos\Backup\Photos\...`), so "resume" never finished. Now refused, like Explorer: *can't copy ... into itself* | `TestCopyRefusesADestinationInsideTheSource`, `TestPlanLocalRefusesCopyingIntoItself` |
| 2 | `search --copy-to` put two drives with the same label (e.g. two "USB DRIVE" pen drives) into one folder | same-named files overwrote/skipped each other. A shared label now gets the drive id added: `USB DRIVE (vol-1A2B3C4D)` | `TestSearchCopyToKeepsSameLabelSourcesApart` |
| 3 | Phone file names Windows can't store (`meeting 10:30.txt`, `what?.txt`, `con.txt`) were copied as-is | a `:` on NTFS silently writes an *alternate data stream* of a file called `meeting 10` instead of the file; `?`/`*` failed. Now `<>:"\|?*`, backslashes, control chars and trailing dots/spaces become `_`, device names get a `_` prefix, and such files are pulled one at a time to the safe name (`adb pull -a <remote> <local file>`) | `TestPhoneCopyMakesNamesSafeForWindows`, `TestSafeName` |
| 4 | `size:>99999999999tb` / `size:>9223372036854775807` overflowed int64 | wrapped round to a negative minimum: matched **every** file instead of none | `TestHugeSizesDoNotWrapAround` |
| 5 | `modified:<300000d` overflowed `time.Duration` (max ~292 years) | silently meant "< 292 years" | `TestHugeRelativeDates` |
| 6 | `ext:tar.gz` compared only the text after the last dot | multi-part extensions never matched anything | `TestMultiPartExtensions` |
| 7 | Phone listings with `//`, `./` or `../` in a path (found by the fuzzer) | folders with an empty name (shown as `DCIM\\Camera`), and two spellings of one folder became two folders | `TestOddPathSpellingsShareOneFolder`, `FuzzParser` |
| 8 | `stale_after = "300000d"` (meant as "never") overflowed to a negative duration | every index was reported stale on every run | `TestHugeStaleAfterMeansNeverStale` |
| 9 | Sizes at a unit boundary printed as `1024 KB` / `100.0 KB` | should be `1.0 MB` / `100 KB` | `TestHumanSizeRoundsAcrossUnits` |

What was run (all in the cloud container, Linux, Go 1.26):
- **Fuzzing** (new `Fuzz*` tests; their seeds also run on every `go test`): `.ddx` index reader (`FuzzRead`, ~4M inputs - corrupt files always give `ErrCorruptIndex`, never a panic, and anything that loads round-trips), NTFS USN record parser (`FuzzParseRecords`, ~5.4M), phone `find`/`stat` parser (`FuzzParser`, ~4.4M after the fix) and `adb devices` parser (`FuzzParseDevices`, ~4.8M), query language (`FuzzParse`, ~1M twice). Run one with e.g. `go test ./internal/index -run '^$' -fuzz FuzzRead -fuzztime 60s`.
- **Randomized cancel/resume stress** (`TestStressCancelAndResume`, skipped with `-short`): 1,500 files sized around the 1 MB copy buffer (0, 1, 1 MB-1, 1 MB, 1 MB+1, 3 MB+7 bytes, random), copy cancelled at a random file 4 times (with and without `--verify`), then completed: byte-identical, no `.ddxpart` leftovers, a re-run writes nothing. Passed 3x under `-race`.
- **End-to-end with the real binary, 200,000-file fixture** (202,720 entries): walk and parallel scanners both indexed exactly what `find` sees (1.0 s / 352 ms); 11 queries (`ext:`, `type:`, `size:` ranges, `!word`, `re:`, `modified:`, `path:`) returned exactly the same counts as an independent Python implementation; full copy interrupted with Ctrl+C after 14,695 files, re-run copied the remaining 185,305 → `diff -r` identical, third run "Everything is already there"; 25 files edited → `--dry-run` said "overwrite 25", `--verify` copied exactly those; `search ext:jpg --copy-to` copied all 49,550 matches; corrupted / truncated / empty `.ddx` files → a warning with the fix, other indexes still searched, `list` shows `(unreadable)`.
- Whole suite: `go vet` (linux, windows/amd64, windows/arm64), `go test ./...` 4x (3x with `-shuffle=on`), `go test -race ./...`, Windows cross-builds of both programs and of the test binaries.

Noticed but left alone (not bugs, or not worth the code): `doctor` reports "N indexes saved" without flagging an unreadable one (`list` and every search already do); a phone file named `a:b.jpg` and another named `a_b.jpg` in the same folder would map to the same Windows name.

## Deviations from BUILD.md
- Stage 1: `internal/index/model.go` and `path.go` were created in stage 1 (BUILD.md lists them under stage 2) because the `Scanner` interface (section 7.5) takes an `*index.Builder`. Stage 2 adds the file format, store and search on top.

- Stage 1: `ui` also contains console setup (ANSI colors + UTF-8 code page on Windows, restored on exit) and the one-line status display; BUILD.md describes these later but every command needs them from the start.
- Stage 12: **PATH is edited in the registry from Go, not with the PowerShell snippet in BUILD.md.** `[Environment]::SetEnvironmentVariable('Path', ..., 'User')` first *expands* the existing value (so `%USERPROFILE%\bin` becomes a fixed path) and rewrites it as a plain string - quietly damaging a PATH the user may have set up on purpose. `internal/install` reads the raw `HKCU\Environment\Path`, appends the folder (everything else kept byte for byte), writes it back as `REG_EXPAND_SZ` and broadcasts `WM_SETTINGCHANGE` (what the PowerShell call does for notification) so new terminals see it. The add/remove/"already there?" logic is plain, tested code (case, quotes, trailing slash, `%VARS%`, round-trips); only ~40 lines (registry value + `SendMessageTimeoutW`) are Windows-only and can't be run here - owner check below.
- Stage 12: `drivedex install` asks y/N **before every step** (copy / PATH / right-click menu / start-up; doctor is read-only) and each step can be declined on its own; `--yes` answers all. The menu and start-up entries are written for the *installed* copy (`%LOCALAPPDATA%\Programs\DriveDex\...`), not the downloaded one (tested). If the agent is running during an upgrade it is stopped for the copy and the installed one is started again. Files are copied to `<name>.new` and renamed over the old ones, so a failed copy never leaves half a program. `scripts/install.ps1` only locates `drivedex.exe` and runs `drivedex.exe install` (one implementation, not two); it deliberately does **not** run `Unblock-File` or touch execution/SmartScreen settings (BUILD.md: never change security settings) - the README explains "More info -> Run anyway".
- Stage 12: `drivedex uninstall` reverses each step with its own y/N. **Your data is never deleted by `--yes`**: indexes, the agent log and `config.toml` are only removed if you answer `y` to the final question or pass `--purge`. It lists/deletes DriveDex's own files by exact name/extension (`*.ddx`, `*.ddx.tmp`, `*.lock`, `agent.log`, `agent.pid`, `config.toml`) - never a folder tree; folders are removed only when empty. A program can't delete its own running `.exe` on Windows, so when `uninstall` runs from the installed copy it starts a hidden `cmd /c ping ... & del <exact files> & rmdir <folder>` that runs a few seconds after it exits (`rmdir` without `/s`: refuses to remove a non-empty folder; paths containing `%` or `"` are refused with a "delete it by hand" message). `install`/`uninstall` still work when `config.toml` is broken.
- Stage 12: `scripts/build.ps1` also takes `-SkipChecks` (CI has just run vet/test) and puts `install.ps1` in the zips next to both programs, README and LICENSE; after building it leaves `bin\drivedex.exe`/`drivedex-agent.exe` for the host CPU (the earlier stages' instructions use that path). Verified here only by cross-compiling exactly the same `go build` lines (amd64 and arm64, agent = GUI subsystem, 5.6 MB console exe) - **PowerShell isn't available in the cloud container, but GitHub's `windows-latest` runner ran `build.ps1` (PowerShell 7) successfully in CI (run 3, commit `5e7c595`) and uploaded the zips (7.9 MB artifact).** Not yet run by anyone: `install.ps1`, and either script under Windows PowerShell 5.1 (the one built into Windows) - owner check below.
- Stage 12: CI has three jobs: Windows (vet, test, `build.ps1 -SkipChecks`, upload zips), an extra Linux job running the **race detector** (needs CGO + gcc, which the Windows runner/owner PC may lack), and a release job on `v*` tags (needs both, attaches the zips with `softprops/action-gh-release`). The Windows job is the **first time the whole test suite runs on Windows** (earlier stages could only be cross-compiled/vetted there), so failures that are really test-portability problems (path separators, file modes) are possible and are the first thing to look at.
- Stage 12: **first full test run on Windows (GitHub Actions, windows-latest) found 1 real bug and 2 test-portability problems, all fixed:** (1) *real bug* - the TUI's "No matches." hint was shown only when `took > 0`, but on Windows a fast search can measure as 0 elapsed, so the hint never appeared there; it now uses an explicit "a search has finished" flag (`TestNoMatchesHintDoesNotDependOnTimer`). (2) a test asserted "not running as Administrator" but the CI account *is* an administrator - the test now fakes `isElevated`. (2) The demo GIF - needs a screen recording on Windows; the README has a placeholder and ScreenToGif instructions. (3) The `v1.0.0` tag/release - BUILD.md says to ask first.
- Stage 11: **`doctor --bench` only deletes a file it created.** BUILD.md says "always deletes the file"; the test file is opened with `O_EXCL`, and if `E:\.drivedex-bench.tmp` already exists the test refuses (naming the file) instead of overwriting and then deleting something DriveDex didn't create (BUILD.md rule: never delete user files). Everything DriveDex *did* create is removed on success, on any error and on Ctrl+C (`defer`; the file is closed first because Windows can't delete an open file; a failed delete is reported with the path). Free space (600 MB) is checked before anything is written; nothing is written without a `y` unless `--yes`. Random data is written (one 4 MB chunk reused) so a compressing controller can't flatter the result. Boundaries: < 25 MB/s ❌, 25-60 MB/s (60 included) ⚠️, > 60 MB/s ✅.
- Stage 11: `doctor` is split into **Facts (collected by the CLI from Windows) and `doctor.Build` (pure logic)**, so every message and fix tip is unit-tested without a PC (`internal/doctor`). Extras beyond the table: FAT32 ("can't hold a file over 4 GiB") warning, adb version, per-phone state tips (`unauthorized` → tap Allow), network drives and empty card-reader slots are left out, the NTFS journal is only opened when elevated (otherwise a dim "not checked"). Doctor itself writes only one thing: a temp file inside DriveDex's own index folder to prove it is writable (deleted at once).
- Stage 11: **config** is loaded in `PersistentPreRunE` into `activeConfig`; `config`, `doctor`, `version`, `help`, `completion` still run with a *broken* file (they are how you find and fix it; doctor reports the line). Wired: `default_limit`, `show_hidden` (search + TUI), `workers` (index/copy/TUI-indexing; an explicit `--workers` wins), `skip_dirs`+`skip_dirs_extra` (walk, parallel, MFT scan *and* journal replay via `ntfs.Session.SkipDirs`), `stale_after` (search tips, doctor, agent catch-up), `adb_path` (CLI and agent), `phone_root` (indexing, header RootPath, `copy phone:/...`), `color` (+ `NO_COLOR`, `--no-color`), and for the agent `notifications` and `auto_index`. The agent reads the file when it starts (`drivedex agent stop` then `start` after changing those two). A changed `skip_dirs` applies at the next *full* scan (for NTFS turbo mode: `index E: --full`) — noted in the generated file. `DRIVEDEX_CONFIG` overrides the file location (tests use it, so they never touch a real settings folder).
- Stage 11: **query language** = `internal/query` (parser + `index.Matcher`), table-driven tests for every row of BUILD.md's table plus error wording. A lone `!word` is a valid search (everything except...). `size:`/`modified:` skip `FlagNoMeta` entries and `search` prints the specified tip once (stderr in `--json`/`--paths-only` mode). In the TUI, a half-typed filter such as `size:>` does **not** blank the results: the last good results stay and the footer says what is missing (typing `size` letter by letter would otherwise flicker an error). Drive filter `drive:E` matches the drive *currently* at E: (or last seen there), `drive:phone` any phone, `drive:"SANDISK 32GB"` a label or index id. `path:` and `re:` run only on entries that already passed the cheap filters (benchmark below: 1,000,000 entries, every query under 75 ms).
- Stage 11: **`search --copy-to <dir>`** copies *every* match (the display limit is ignored), but only **files** — matching folders are skipped with a one-line note (copying a folder would silently pull in everything under it, which a search for `photos` surely doesn't intend). Each source gets its own sub-folder named after its label (two drives can hold identical names), keeping the file's folder structure. Matches on drives/phones that aren't connected are skipped *with a message naming them*; more than 100 files asks y/N first (`--yes` skips; anything but y/yes, including no input, means no). Reuses the stage 7 planner (`copier.PlanJobs` / new `PlanPhoneJobs`) so skip/overwrite/`.ddxpart`/staging behave exactly like `copy`. `--json`/`--paths-only` keep stdout machine-clean (the "Nothing indexed yet" message goes to stderr, an empty result is `[]`).
- Stage 11: help polish: every command has `Short`, `Long` and two or more `Example`s (enforced by `TestEveryCommandHasShortLongAndExamples`, which walks the whole command tree). `drivedex completion powershell` is cobra's built-in; the README (stage 12) documents how to enable it.
- Stage 10: **deviation from BUILD.md's command lines (spec bug):** the spec uses `"<exe>" tui --scope "%1"` and `"<exe>" index "%1" --pause`. For a drive Explorer passes `E:\`, and in `"E:\"` Windows reads `\"` as an *escaped quote*: the program receives `E:" --pause` as one argument (`--pause` swallowed, scope corrupt). Same for `%V` when you right-click inside a drive's root window. The entries therefore use `"%1 "` / `"%V "` (a trailing space inside the quotes), and every path argument is already space-trimmed (`resolveRoot`). `internal/shellint/menu_test.go` contains a faithful implementation of the documented `CommandLineToArgvW` rules and proves both the failure of the spec's form and the success of the fix (drive roots, `%V` on a drive root, folders with spaces/Unicode).
- Stage 10: `shell uninstall` deletes exactly the four keys (and their `command` sub-keys) and, before deleting, checks the key's command mentions `drivedex` — a different program's key that happens to be named `DriveDex` is left alone and reported. `shell install` asks y/N first (BUILD.md: ask before registry edits) unless `--yes`, lists the keys it will write, and is idempotent (re-running from a new location repairs entries after the program moved; `shell status` reports `missing` / `points to a different drivedex.exe`).
- Stage 10: `--pause` is a global flag handled in `Execute`: after the command finishes (success or failure — the error is printed first) it prints `Press Enter to close…` and waits. The "This drive isn't indexed yet. Press I…" prompt inside the TUI was already built in stage 8.
- Stage 9: the agent **re-indexes by running `drivedex index <E:|phone:SERIAL>`** (the CLI installed next to it, hidden window) instead of duplicating indexing logic. The agent therefore gets NTFS turbo mode (when elevated), incremental refresh, and the lock for free; the entry count for the log/notification is read back from the saved index header (no output parsing). Consequence: `drivedex.exe` and `drivedex-agent.exe` must be installed together (stage 12's installer does this).
- Stage 9: the lock file (`<id>.lock`, `O_CREATE|O_EXCL`) is taken by **the CLI `index` command** (so the agent and a hand-run `index` can't collide); the agent only *checks* for a fresh lock before launching its child (taking it itself would block its own child). A lock older than 10 min is stale and taken over; a holder touches its lock every minute so a long scan is never mistaken for a crash (BUILD.md didn't specify the refresh).
- Stage 9: **start-up catch-up (not in BUILD.md):** drives/phones already connected when the agent starts are indexed once if their index is missing or older than 24 h, otherwise an always-plugged-in USB disk would never be indexed by the agent. Drives present at start are otherwise not treated as "arrivals".
- Stage 9: polling = cheap `GetLogicalDrives()` bitmask every 2 s as specified, **plus** a full look every 10 s for removable drives, because inserting an SD card into a card reader doesn't change the drive-letter mask. The agent lists drives with `volume.ListLocal` (skips network shares, which can block for many seconds when disconnected). Bus type (USB) comes from `IOCTL_STORAGE_QUERY_PROPERTY` (`volume.BusType`); a drive whose bus can't be read is treated as non-USB (logged once). Indexing is serialized on one worker so several USB drives don't fight over the bus.
- Stage 9: toast text is "<label> indexed" / "N entries" (BUILD.md's example says "files", but the number is entries = files + folders). The PowerShell toast script quotes the text as single-quoted strings, so a drive label can't inject commands (tested).
- Stage 9: `startup enable` writes exactly **one** start-up mechanism (the Run value, or with `--elevated` the scheduled task and removes the Run value), so two agents never race at log-in; both enabling paths ask y/N first (BUILD.md: ask before editing the registry / creating the task) unless `--yes`.

(2) the tray icon — `fyne.io/systray` **does** build with `CGO_ENABLED=0` for Windows (checked in a scratch module), but it needs an icon asset and a GUI message loop that I can't see render. - Stage 8: sizes/dates for entries the index doesn't know (NTFS turbo-mode indexes) are looked up with `os.Lstat` **only for rows currently on screen**, and only for drives that are connected; the result is kept in the row, never written back into the shared index (searches run concurrently).
- Stage 8: the `--scope` "not indexed yet — Press I to index now" prompt (BUILD.md lists it under stage 10) was implemented here because scope handling lives in this model; stage 10 only has to add the right-click entries and `--pause`. `I` indexes the *whole drive* the scope folder is on (or just the folder if it isn't on an identifiable drive), silently (`scanOptions.quiet`).
- Stage 8: scope matching is `index.ScopeMatcher`: the cheap name test runs first, the ancestor walk only for name matches. `index.LocateScope` finds the covering index from the folder path (volumes via current mount, folder sources via RootPath; longest root wins).
- Stage 8: Bubble Tea's package `init()` asks the terminal for its background colour (OSC 11) at process start on **Unix-like** terminals (a terminal that never answers makes that wait up to ~5 s). termenv does **not** do this on Windows (it returns defaults), so it doesn't affect the owner's PC; noted in case the tool is ever used on Linux/macOS.
- Stage 7: `copy` is built around a plan/run split (`copier.Plan` of `Item`s = a `Job` + a `Decision`), so stage 11's `search --copy-to` can reuse it with `copier.PlanJobs` (an explicit file list). Conflict decisions are made at *plan* time (needed for `--dry-run` and the free-space/FAT32 pre-checks); progress counts skipped files as done immediately, and the byte total counts only files that will be written.
- Stage 7: pre-checks only count files that will actually be written (BUILD.md says "total bytes"); a huge file that is being skipped can't block a copy to FAT32.
- Stage 7: `adb pull` is **staged**: each batch is pulled into a hidden `.ddxpull-*` folder inside the destination and files are renamed into place only when they arrived, so an interrupted pull can never leave a half-written file under its real name (which a later run might otherwise accept as "same size/time" or "newer"). BUILD.md pulls straight into the destination. Stale staging folders are removed at the start of the next run. Failed batch members are retried one file at a time (2 retries). `--verify` is not available for phone copies (nothing local to compare against) — the command says so.
- Stage 7: links/special files are never followed (a symlink's target is not copied); they are counted as skipped. A failed `--verify` deletes the bad copy (it would otherwise look "already there" to the next run). Ctrl+C removes the partial `.ddxpart` files it was writing and exits 0 after printing the resume hint (only failed files give a non-zero exit).
- Stage 7: phone paths are relative to the phone's storage as shown by `search` (`phone:/DCIM/Camera` = `/sdcard/DCIM/Camera`); `/sdcard/...` and `/storage/...` are taken literally. Copying *to* a phone is refused (DriveDex never writes to a phone).
- Stage 6: the NTFS logic is split so almost all of it is testable off-Windows: `ntfs.Device` (a one-method interface: `IOControl(code, in, out)`) hides `DeviceIoControl`; Windows error numbers are translated to sentinel errors (`ErrEOF`, `ErrJournalNotActive`, `ErrJournalEntryDeleted`, `ErrNeedAdmin`, ...) in `mft_windows.go`. `internal/ntfs/ntfstest` is an in-memory fake NTFS volume (MFT, metafiles, System Volume Information, a real journal with trim/reset) used by the ntfs and cli tests. The only code that cannot run here is the ~60-line `mft_windows.go` + `IsElevated` — it is type-checked with `GOOS=windows go vet/build`.
- Stage 6: the skip list (System Volume Information, $RECYCLE.BIN) is applied at **any depth** in MFT mode, matching `walk`/`parallel` (BUILD.md says "root level"); results stay comparable between scanners.
- Stage 6: collected MFT records are kept in a slice, not the `map[uint64]rec` BUILD.md suggests — a map for millions of records costs far more memory; reachability uses one `map[frn]slot` plus a memoized state array.
- Stage 6: journal replay drops (and un-indexes) any record whose parent folder isn't in the index — otherwise constant churn inside System Volume Information would pollute the index with `?\` orphans on a real C: drive. "N changes applied" counts *distinct* files changed, not journal records (one file save writes several records).
- Stage 6: `--mode mft` that can't be honoured (not Administrator / not NTFS / no journal) is an **error with a fix**; `--mode auto` falls back silently-with-a-note instead. Added `--full` (skip incremental refresh) next to the specified `--with-metadata`. `--with-metadata` never uses the refresh shortcut (a refresh would lose the metadata).
- Stage 6: lazy size/date lookup (`index.FillMeta`) runs for displayed `search` results of connected volume/folder sources; phones are skipped. Not persisted.
- Stage 5: all adb access goes through a small `phone.Runner` interface (real one = `ExecRunner`, tests use `internal/phone/phonetest`), so every adb behaviour is unit-tested without a phone, including on Windows CI (the `ExecRunner` tests start the Go test binary itself as a stand-in adb).
- Stage 5: fallback to the names-only `find` triggers when the stat listing produced **no usable lines** and either exited non-zero *or* printed only unparseable lines (BUILD.md only mentions non-zero exit; the extra case covers a stat that prints an error but exits 0). A non-zero exit that *did* produce lines is accepted (find exits 1 when any folder, e.g. `Android/data`, is protected).
- Stage 5: `adb` is only started during `search`/`list` when at least one phone index exists, with a 5 s timeout, so people without phones never pay for it; if adb is missing, phones simply show as `· offline` (never an error).
- Stage 5: hints may now be multi-line (setup steps), printed aligned under `Fix:`. `adb_path` config is wired in stage 11 (`phone.FindADB(configured)` already takes it).
- Stage 5: names-only phone entries carry `FlagNoMeta` per spec; stage 6's lazy `os.Lstat` metadata fill must **skip phone sources** (a phone path isn't a local file).
- Stage 4: `index` also gained `--mode`/`--workers` (as specified); `scan.AutoWorkers` (portable) holds the HDD/flash/unknown → 2 / min(16, 2×CPUs) / 4 rule, `volume.SeekPenalty` (Windows IOCTL, stub elsewhere) supplies the input. `bench-scan` always uses the *parallel* scanner (1 worker = parallel with one worker), not `walk`.
- Stage 4: the parallel scanner reads folders with `File.ReadDir(-1)` (unsorted) instead of `os.ReadDir` (sorted) because order doesn't matter and sorting every folder is wasted work; `readDir` is a package variable so tests can inject failing folders.
- Stage 4: race test **was run** (`CGO_ENABLED=1 go test -race ./internal/scan/ ./internal/index/`, gcc available in the cloud container): clean. The owner's PC may have no C compiler; CI runs without `-race` (CGO off) — see stage 12.
- Stage 3: hooks `listVolumes` / `volumeForPath` in `internal/cli/volumes.go` let tests simulate drives being plugged in/out/renumbered on Linux. Real Windows calls only run on the owner's PC (`volume_windows_test.go` is checked to compile via `GOOS=windows go vet`).
- Stage 3: a drive with serial `0` (can happen on odd network drives) is indexed as a plain *folder* source instead of colliding on `vol-00000000`.
- Stage 3: `forget` also accepts the last-seen letter of an unplugged drive and can remove an unreadable (corrupt) `.ddx` file; it matches by id, then letter, then label, and refuses ambiguous matches.
- Stage 3: stale-index tips print one dim line per stale *connected* drive (BUILD.md says "one dim line"; with several stale drives each gets its own line).
- Stage 2: search takes a `Matcher` interface (`index.Search(indexes, matcher, opts)`) instead of a plain term list, so stage 11's query language can reuse the parallel search/ranking code. `TermMatcher` is the stage 2 implementation.
- Stage 2: `internal/index/display.go` (BUILD.md section 7.6 display paths + online/offline `Env`) was written in stage 2 rather than 3, since `search` needs it for folder sources; stage 3 only has to fill `Env.Mounts` from the real drive list.
- Stage 2: extras beyond the file list: `index.Store.List()`/`ReadHeaderFile` (header-only reads for stage 3's `list`), `source.go` (folder source IDs), env var `DRIVEDEX_INDEX_DIR` to relocate the index folder (used by tests; handy for the owner too), and SourceIDs are sanitised into safe file names (e.g. wireless-adb serials contain `:`).
- Stage 1: `--limit` on `scan` caps the *printed* lines only; the summary still counts the whole scan.
